# Prisma layer — operating rules

**Prisma ORM 7.10.x · PostgreSQL 17**
Companion to `../DATA-MODEL.md` v1.0

---

## 1. The schema is two files, and both are required

| File | Holds | Generated by |
|---|---|---|
| `schema.prisma` | Models, relations, referential actions, plain indexes and uniques | Hand-written; drives `prisma migrate` |
| `migrations/20260912000001_integrity/migration.sql` | CHECK constraints, partial unique indexes, `NULLS NOT DISTINCT`, the `citext` extension, the append-only trigger | Hand-written; **never regenerated** |
| `migrations/20260912000002_project_host_coherence/migration.sql` | `assert_project_host_is_owner()` function + two `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED` (`trg_projects_host_is_owner`, `trg_members_host_is_owner`) — the `owner_id` ⇔ `HOST` row backstop from the `projects` slice (design.md §3.2) | Hand-written; **never regenerated** |

> **Applying `schema.prisma` alone produces a database that accepts invalid models.** It would allow two hosts on one project, a composite association end with multiplicity `*`, an operation log that can be rewritten, two root classes with the same name, and a `LOCKED_BY_HOST` diagram with no host. Prisma simply has no syntax for any of those rules.

This is a known boundary of the tool, not a defect in it. The point is to know where the boundary is, rather than discover later that half the integrity design silently never shipped.

## 2. What Prisma can and cannot express

| Feature | Prisma 7.10 | Where it lives here |
|---|---|---|
| Models, fields, relations | Yes | `schema.prisma` |
| `onDelete: Restrict` — **the FR-C07 guarantee** | Yes | `schema.prisma` |
| Plain and composite unique constraints | Yes | `schema.prisma` |
| Native PostgreSQL enums | Yes | `schema.prisma` |
| `Decimal`, `Bytes`, `Inet`, `Citext`, `Timestamptz` | Yes | `schema.prisma` |
| **CHECK constraints** | **No** | `migration.sql` |
| **Partial indexes** (`WHERE …`) | Preview (`partialIndexes`, since 7.4) | `migration.sql` — see §4 |
| **Expression indexes** (`lower(x)`) | **No** | Avoided entirely — see §3 |
| **`NULLS NOT DISTINCT`** | **No** | `migration.sql` |
| **Triggers, functions, extensions** | **No** | `migration.sql` |

## 3. Two decisions in `DATA-MODEL.md` that the ORM changed

Both were correct as SQL and wrong as Prisma. Recording them so the divergence is deliberate.

### 3.1 `citext` instead of `lower()` indexes — reverses DATA-MODEL.md §1.10

The original design used `text` with `CREATE UNIQUE INDEX ON users (lower(email))`, specifically to avoid an extension. That call was made before the ORM was in the picture.

Prisma cannot express expression indexes, so a `lower()` index would be invisible to it — and invisible objects are exactly what Prisma's drift detection tries to drop. `citext` moves the behavior into the *column type*, which Prisma does understand (`@db.Citext`), so a plain `@unique` is case-insensitive and fully declared in the schema.

One extension, created in `migration.sql`, in exchange for removing a permanent source of migration drift. Applied to `User.email` and `DiagramJoinCode.code`.

### 3.2 UML names stay case-**sensitive** — resolves open item D5

`DATA-MODEL.md` left open whether element names should compare case-insensitively, and its draft indexes used `lower(name)`.

They should not. UML `NamedElement` names are case-sensitive, and so is the Java the code generator emits (FR-F02): `Order` and `order` are different types, and collapsing them would make two valid classes collide. Case-sensitive comparison is also the default, which means `@@unique([enumerationId, name])` and `@@unique([operationId, position])` are plain Prisma constraints with no raw SQL at all.

**D5 is resolved: case-sensitive.**

## 4. Partial indexes — why they are in SQL, and the path out

Prisma 7.4 added a `partialIndexes` preview feature giving `@@index`/`@@unique` a `where` argument. Version 7.10 has it.

They are still in `migration.sql` here for one reason: a preview feature's expression grammar is not something to guess at while writing a schema that has to be correct on the first run. Verify it against the installed version, then migrate these four indexes into `schema.prisma` — that removes the drift problem in §5 entirely, and is worth doing:

- `uq_project_single_host`
- `uq_join_code_active`
- `uq_attribute_name_per_owner`
- `uq_parameter_single_return`

`uq_element_name_per_parent` must stay in SQL regardless — it needs `NULLS NOT DISTINCT`, which has no Prisma equivalent.

**The distinction that decides placement:** partiality that is *semantic* (a rule, like "one HOST per project") goes in SQL where it is guaranteed. Partiality that is merely an *optimization* (skipping soft-deleted rows in a lookup index) is declared as a plain `@@index` in Prisma, because losing the `WHERE` costs a little efficiency and nothing else.

## 5. Migration workflow — the drift trap

Prisma compares `schema.prisma` against a shadow database. Objects it cannot express are invisible to it, so **`prisma migrate dev` will offer to drop them**. Accepting that once removes the integrity layer without any error.

**The rules:**

1. Never run bare `prisma migrate dev`. Always:
   ```bash
   npx prisma migrate dev --create-only --name <what_changed>
   ```
   Review the generated SQL, then `npx prisma migrate dev` to apply.

2. **If a generated migration contains `DROP CONSTRAINT ck_…`, `DROP INDEX uq_…`, or `DROP TRIGGER`, delete those lines before applying.** They are drift artifacts, not intended changes.

3. `20260912000001_integrity` and `20260912000002_project_host_coherence` are both immutable. New constraints go in a *new* hand-written migration, never by editing either of these.

3b. `20260912000002_project_host_coherence` adds `trg_projects_host_is_owner` and `trg_members_host_is_owner` (plus the `assert_project_host_is_owner()` function they call). Prisma does not see triggers or functions — same blind spot as everything else in this file — so a bare `prisma migrate dev` will offer to `DROP TRIGGER` these two. **Never accept that.** Apply this migration only with `prisma migrate deploy`.

4. Never run `prisma db push` against any database that matters. It reconciles by dropping what it does not recognize.

5. CI runs `prisma migrate deploy` (which only applies committed migrations) followed by the constraint smoke test in §7.

## 6. Setup

```bash
npm install prisma@7.10 @prisma/client@7.10
```

> **Pin the version explicitly.** The npm `latest` tag for `prisma` currently points at an `8.0.0-rc`; an unpinned install pulls a release candidate.

Prisma 7 is ESM-first. In `tsconfig.json`:

```json
{ "compilerOptions": { "module": "ESNext", "moduleResolution": "bundler" } }
```

`prisma.config.ts` sits at `apps/api/`, next to `package.json`. In Prisma 7 the connection string lives here, not in the `datasource` block — and the environment is **not** loaded automatically any more, so it is loaded explicitly:

```ts
import { config as loadEnv } from "dotenv";
import { defineConfig, env } from "prisma/config";
import { dirname, resolve } from "node:path";
import { fileURLToPath } from "node:url";

const here = dirname(fileURLToPath(import.meta.url));
loadEnv({ path: resolve(here, ".env") });

export default defineConfig({
  schema: resolve(here, "prisma/schema.prisma"),
  migrations: { path: resolve(here, "prisma/migrations") },
  datasource: { url: env("DATABASE_URL") },
});
```

> Every path is anchored to this file rather than to `process.cwd()`, so the CLI behaves identically whether it runs from `apps/api` or from the repo root through `npm run --workspace`.

The client is generated to `src/generated/prisma` (Prisma 7 requires an explicit `output`; it no longer writes into `node_modules`):

```ts
import { PrismaClient } from "../generated/prisma/client";
```

Add `src/generated/` to `.gitignore`.

## 7. Verify the integrity layer actually applied

These are the cheapest possible regression tests, and they catch the failure mode this whole document exists to prevent — a migration that silently dropped the constraints. Each must **fail**:

```sql
-- 1. Two hosts on one project        → uq_project_single_host
INSERT INTO project_members (project_id, user_id, role) VALUES ($p, $u2, 'HOST');

-- 2. Composite end with multiplicity * → ck_composite_multiplicity
UPDATE uml_relationship_ends SET aggregation = 'COMPOSITE', upper_bound = NULL WHERE id = $e;

-- 3. Rewriting history               → trg_operations_append_only
UPDATE diagram_operations SET payload = '{}'::jsonb WHERE id = $o;

-- 4. Two root classes named the same → uq_element_name_per_parent (NULLS NOT DISTINCT)
INSERT INTO uml_elements (diagram_id, parent_id, kind, name) VALUES ($d, NULL, 'CLASS', 'Order');
INSERT INTO uml_elements (diagram_id, parent_id, kind, name) VALUES ($d, NULL, 'CLASS', 'Order');

-- 5. Frozen diagram with no host     → ck_diagrams_lock_coherent
UPDATE diagrams SET lock_state = 'LOCKED_BY_HOST', locked_by = NULL WHERE id = $d;
```

And one that must **succeed**, because operation overloading is legal UML and `uq_attribute_name_per_owner` is deliberately partial:

```sql
-- Two operations named `calcular` on the same class, different signatures
INSERT INTO uml_features (owner_id, kind, name) VALUES ($c, 'OPERATION', 'calcular');
INSERT INTO uml_features (owner_id, kind, name) VALUES ($c, 'OPERATION', 'calcular');
```
